1 Cos'è Docker?

Docker è una piattaforma open-source che automatizza il deployment, la scalabilità e la gestione delle applicazioni. Utilizza la containerizzazione per impacchettare un'applicazione insieme a tutte le sue dipendenze, garantendo che il programma si esegua in modo identico su qualsiasi macchina: il portatile dello sviluppatore, il server di test, il server di produzione.

A differenza delle macchine virtuali tradizionali, i container condividono il kernel del sistema operativo host mantenendo l'isolamento tra loro. Questo li rende molto più leggeri: avvio in millisecondi, utilizzo minimo di RAM, nessuna installazione di un intero sistema operativo per ogni istanza.

Container vs Macchina Virtuale

Terminologia essenziale
Image: snapshot read-only con tutto il necessario per eseguire l'app (codice, runtime, librerie).
Container: istanza in esecuzione di un'image — si crea, si avvia, si ferma, si elimina.
Dockerfile: file di istruzioni che descrive come costruire un'image passo per passo.
Registry: repository di image; il più noto è Docker Hub (hub.docker.com).

2 Come Docker supporta la pipeline CI/CD?

CI/CD sta per Continuous Integration (integrazione continua) e Continuous Deployment (deploy continuo). È una pratica che automatizza le fasi di build, test e rilascio del software: ogni volta che uno sviluppatore fa un push del codice, la pipeline si avvia automaticamente e produce una nuova versione verificata e pronta per il deploy.

Docker risolve uno dei problemi più classici dello sviluppo software — il famoso "funziona sul mio PC!" — garantendo che l'ambiente di esecuzione sia identico in ogni fase: sviluppo locale, server di CI, staging e produzione usano la stessa image.

Il flusso CI/CD con Docker

Perché Docker rende la CI/CD più efficace

VantaggioSpiegazione
Ambiente identico ovunque Il Dockerfile definisce l'ambiente una volta sola: sviluppo, CI e produzione usano esattamente la stessa image. Nessuna sorpresa al deploy.
Build riproducibili Ogni build parte dalla stessa image di base: i risultati sono deterministici e non dipendono dallo stato del server di CI.
Velocità di avvio I container si avviano in pochi secondi: la CI può lanciare test isolati rapidamente e parallelizzarli su più container.
Versioning delle image Ogni commit produce un'image con tag univoco su Docker Hub: si può sempre tornare a una versione precedente con docker pull nome:tag.
Integrazione con i tool CI/CD GitHub Actions, GitLab CI, Jenkins e altri supportano nativamente Docker: bastano pochi step YAML per automatizzare tutto il ciclo.

3 Consigli dall'esperto

Tony Kelly, esperto di DevOps, indica cinque strategie per ottimizzare la CI/CD con Docker. Vediamo come si applicano concretamente al nostro progetto.

Consiglio 1

Multi-stage build

Usa build multi-stage per ridurre la dimensione dell'image finale. Il nostro Dockerfile separa già lo Stage 1: Build (JDK + Ant) dallo Stage 2: Runtime (solo il JAR).

Consiglio 2

Docker layer cache

Ordina le istruzioni COPY dal meno al più frequentemente modificato: le dipendenze (lib/) prima dei sorgenti (src/). Docker riusa i layer invariati, velocizzando le rebuild.

Consiglio 3

Test parallelizzati

Nei pipeline più avanzati si aggiunge uno stage dedicato ai test nel Dockerfile (FROM build AS test). GitHub Actions può eseguire più job in parallelo su container separati.

Consiglio 4

Layer sharing nei runner CI

Abilita la cache di Docker Buildx nel workflow GitHub Actions con cache-from e cache-to. Riduce drasticamente i tempi di build nelle esecuzioni successive.

Consiglio 5

Security scanning

Integra nel workflow tool come Trivy o Docker Scout per rilevare vulnerabilità nelle dipendenze prima che l'image raggiunga la produzione.

4 Tutorial: CI/CD per la Calcolatrice REST

In questo tutorial configureremo una pipeline CI/CD completa per il progetto ServerRest-Calcolatrice-DB-Docker: ogni push sul branch main compilerà automaticamente il progetto Java, costruirà l'image Docker e la pubblicherà su Docker Hub.

Prerequisiti — già completati nei tutorial precedenti
Hai già a disposizione:
  • Il progetto Java con il Dockerfile multi-stage (Stage 1: Build, Stage 2: Runtime)
  • Il file docker-compose.yml per l'orchestrazione locale con MySQL
  • Il file .dockerignore
Servono ancora: un account GitHub (gratuito) e un account Docker Hub (gratuito).

Step 5 — Creare il repository GitHub e configurare le credenziali

  1. Accedi a GitHub e crea un nuovo repository pubblico (es. serverrest-calcolatrice-db-docker).
  2. Nel repository appena creato vai su Settings → Secrets and variables → Actions.
  3. Crea una Repository variable (non secret) chiamata DOCKER_USERNAME con il tuo username di Docker Hub.
    Le variabili sono visibili nei log; i secret sono oscurati. Username non è un dato sensibile, quindi va come variabile.
  4. Vai su Docker Hub → Account Settings → Personal access tokens e genera un nuovo token con permessi di lettura e scrittura. Chiamalo github-actions-calcolatrice.
  5. Torna su GitHub e crea un Repository secret chiamato DOCKERHUB_TOKEN incollando il token appena generato.
  6. Dal terminale, collega il repository locale a quello GitHub e fai il primo push: 
    # Collega il repository remoto
git remote set-url origin https://github.com/TUO-USERNAME/serverrest-calcolatrice-db-docker.git

# Aggiungi tutti i file (Dockerfile, docker-compose.yml, src/, lib/, ecc.)
git add -A
git commit -m "Aggiungi Dockerfile e docker-compose per CI/CD"
git push -u origin main
Non mettere mai le credenziali nel codice
Password e token non devono mai comparire nei file sorgente o nei commit. Usa sempre i GitHub Secrets (${{ secrets.NOME }}) per i dati sensibili e le Repository Variables (${{ vars.NOME }}) per i valori non sensibili.

Step 6 — Configurare il workflow GitHub Actions

GitHub Actions legge i workflow dalla cartella .github/workflows/ del repository. Creiamo il file che automatizzerà la nostra pipeline.

  1. Nel repository GitHub clicca sul tab Actions.
  2. Clicca su New workflow → set up a workflow yourself.
  3. Incolla la seguente configurazione YAML nell'editor e clicca Commit changes: 
.github/workflows/ci.ymlname: CI – Calcolatrice REST

# Il workflow si avvia ad ogni push sul branch main
on:
  push:
    branches:
      - main

jobs:
  build-and-push:
    runs-on: ubuntu-latest

    steps:

      # 1. Clona il repository nel runner
      - name: Checkout del codice
        uses: actions/checkout@v4

      # 2. Autentica il runner su Docker Hub
      - name: Login a Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      # 3. Configura Docker Buildx (supporto multi-piattaforma e cache)
      - name: Configurazione Docker Buildx
        uses: docker/setup-buildx-action@v3

      # 4. Costruisce l'image e la pubblica su Docker Hub
      - name: Build e push dell'immagine
        uses: docker/build-push-action@v6
        with:
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ vars.DOCKER_USERNAME }}/serverrest-calcolatrice:latest
          # Abilita la cache per build più veloci nelle esecuzioni successive
          cache-from: type=gha
          cache-to: type=gha,mode=max

Spiegazione dei passi del workflow

StepAction usataCosa fa
Checkout actions/checkout@v4 Scarica il codice del repository nel runner (la macchina virtuale di GitHub).
Login Docker Hub docker/login-action@v3 Autentica il runner su Docker Hub usando le credenziali salvate nei secret/variable. Necessario per poter fare il push.
Setup Buildx docker/setup-buildx-action@v3 Configura Docker Buildx, il builder avanzato di Docker che supporta multi-piattaforma (amd64 + arm64) e la cache.
Build & Push docker/build-push-action@v6 Esegue il Dockerfile (compilazione Ant + download driver JDBC), costruisce l'image per due architetture e la pubblica su Docker Hub con il tag :latest.
Perché linux/amd64,linux/arm64?
Costruire per entrambe le architetture permette di usare l'image sia su PC Intel/AMD (amd64) sia su Mac con chip Apple Silicon o server ARM (arm64). Docker Hub servirà automaticamente la variante corretta in base all'architettura del sistema che scarica l'image.

Step 7 — Eseguire e verificare il workflow

  1. Scarica il file del workflow appena creato su GitHub nel repository locale: 
    git pull origin main
  2. Apporta una qualsiasi modifica al codice (anche solo un commento) e fai push. Il workflow si attiverà automaticamente: 
    git add -A
git commit -m "Test pipeline CI/CD"
git push
  3. Vai sul tab Actions del repository GitHub. Vedrai il workflow "CI – Calcolatrice REST" in esecuzione con un cerchio giallo animato. Clicca su di esso per vedere i log in tempo reale.
  4. Attendi che tutti i passi mostrino la spunta verde ✓. L'intera pipeline richiede tipicamente 3–5 minuti al primo avvio (download delle image di base), poi ~1 minuto grazie alla cache.
  5. Accedi a Docker Hub → Repositories. Troverai il repository TUO-USERNAME/serverrest-calcolatrice con l'image appena pubblicata, taggata latest.
Pipeline completata con successo
Da questo momento in poi, ad ogni git push su main GitHub Actions ricompilerà automaticamente il progetto Java, costruirà l'image Docker e la pubblicherà su Docker Hub — senza alcun intervento manuale.

Usare l'image pubblicata su Docker Hub

Chiunque abbia il link del repository può ora scaricare ed eseguire la Calcolatrice REST senza nemmeno installare Java o Ant:

# Scarica ed esegui l'immagine direttamente da Docker Hub
docker run -d -p 8080:8080 TUO-USERNAME/serverrest-calcolatrice:latest

# Oppure sostituisci l'immagine nel docker-compose.yml, commentando "build: ."
# e aggiungendo "image: TUO-USERNAME/serverrest-calcolatrice:latest"

5 Best practice per la CI/CD con Docker

Ambiente consistente con i container Docker

Docker garantisce che l'ambiente di esecuzione sia identico su tutte le macchine, incapsulando dipendenze e librerie all'interno del container. Il Dockerfile va mantenuto aggiornato: se cambia una dipendenza (es. nuova versione di Gson), va aggiornato il file e non solo l'installazione locale.

Version control dei Dockerfile

Salvare il Dockerfile in Git (come già facciamo) permette di tracciare ogni modifica, tornare a versioni precedenti e revisionare i cambiamenti tramite pull request prima di integrarli. Ogni immagine pubblicata su Docker Hub dovrebbe avere un tag che corrisponde al commit Git (es. :1.2.0 o :abc1234), non solo :latest.

Tag semantici nel workflow
Per una pipeline più robusta si può aggiungere l'action docker/metadata-action che genera automaticamente tag come :1.0.0, :1.0, :latest basati sui tag Git e sui numeri di versione.

Pulizia automatica delle image non utilizzate

Docker non elimina automaticamente le image obsolete: nel tempo il disco si riempie. È buona pratica configurare una procedura di pulizia periodica.

# Rimuove tutte le image non associate a container attivi o fermi
docker image prune -a

# Rimuove i container fermi da più di 24 ore
docker container prune --filter "until=24h"

# Pulizia generale: image, container, network e cache non in uso
docker system prune -f

Automatizzare il processo di build

Con il workflow GitHub Actions già configurato, ogni push avvia automaticamente la build. Per ambienti più complessi si possono definire più job: uno per il test, uno per la build dell'image, uno per il deploy su un server remoto, ognuno con dipendenze esplicite (needs:).

Ottimizzare le image Docker

Le image piccole si scaricano più velocemente, occupano meno spazio e riducono la superficie di attacco. Le strategie principali:

  • Multi-stage build: già implementato nel nostro Dockerfile — lo Stage 2 contiene solo il JRE e i JAR, non gli strumenti di build.
  • Immagini base minimali: le varianti -alpine sono molto più leggere delle immagini standard. Il file Dockerfile.mac del progetto usa già eclipse-temurin:24-jdk-alpine.
  • .dockerignore: il file .dockerignore del progetto esclude già build/, dist/ e *.db dal contesto di build.

Monitoraggio e logging dei container

In un ambiente di produzione è fondamentale sapere cosa sta facendo il container in ogni momento. Gli strumenti più usati:

ToolFunzione
PrometheusRaccolta di metriche (CPU, memoria, richieste/secondo, errori)

6 Conclusioni

In questo percorso abbiamo costruito un sistema completo che parte dal codice sorgente Java e arriva automaticamente a un'image pronta per il deploy su qualsiasi server. Ricapitolando i passi compiuti:

  1. Containerizzato l'applicazione Java con un Dockerfile multi-stage che scarica le dipendenze e compila con Ant.
  2. Orchestrato la Calcolatrice REST insieme a MySQL in container tramite docker-compose.yml, con rete interna, healthcheck e volume persistente.
  3. Pubblicato il repository su GitHub e configurato le credenziali Docker Hub come secret.
  4. Creato un workflow GitHub Actions che ad ogni push su main compila, costruisce e pubblica automaticamente l'image su Docker Hub.
Prossimi passi — per approfondire
  • Aggiungere uno stage di test nel Dockerfile e un job di test nel workflow.
  • Usare docker/metadata-action per generare tag semantici automatici (:1.0.0, :latest).
  • Aggiungere uno step di security scanning con Trivy o Docker Scout nel workflow.
  • Configurare un secondo job nel workflow per il deploy automatico su un server remoto via SSH.
