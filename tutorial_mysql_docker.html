1 Architettura del sistema

Nella versione precedente il server Java comunicava con un database SQLite embedded: il file calcolatrice.db veniva creato direttamente nella directory di esecuzione. Questa soluzione è comoda ma non scalabile: SQLite non supporta connessioni concorrenti significative e non è adatto a un deploy su più istanze.

Con Docker Compose eseguiamo MySQL in un container separato. I due container — il server Java e MySQL — comunicano tra loro attraverso una rete interna Docker: ogni container è raggiungibile dagli altri usando il proprio nome di servizio come hostname.

SQLite embedded vs MySQL containerizzato

AspettoSQLite (prima)MySQL in container (adesso)
InstallazioneNessuna — driver incluso nel JARContainer mysql:8.0 gestito da Docker
Connessioni concorrentiLimitata (file lock)Piena concorrenza ACID
PortabilitàFile .db legato al filesystem hostDati in volume Docker — indipendenti dall'host
ConfigurazioneParametri hardcoded nel codiceVariabili d'ambiente — zero modifiche al codice al cambio ambiente
Avviojava -cp ... serverrest.Appdocker compose up -d --build

Diagramma dell'architettura

Come funziona il networking interno
Docker Compose crea automaticamente una rete privata condivisa da tutti i servizi definiti nel file docker-compose.yml. All'interno di questa rete ogni container può raggiungere gli altri usando il nome del servizio come hostname. Per questo il server Java usa MYSQL_HOST=mysql: Docker risolve automaticamente mysql nell'indirizzo IP del container MySQL.

2 Modifiche a DatabaseManager.java

Il problema principale con il deploy in container è che i valori hardcoded nel codice sorgente non funzionano: in un container il database MySQL non è su localhost ma su un hostname dinamico (mysql nel caso di Docker Compose). Ogni ambiente (sviluppo, test, produzione) usa credenziali e hostname diversi.

La soluzione è leggere tutti i parametri di connessione da variabili d'ambiente, mantenendo i valori originali come fallback quando la variabile non è impostata. In questo modo il codice funziona sia in locale (SQLite, senza variabili) sia in Docker (MySQL, variabili impostate da docker-compose.yml).

Modifica 1 — Selezione del database (DB_TYPE)

Prima della modifica il tipo di database era una costante fissa a compile-time. Adesso viene letta dall'ambiente a runtime tramite il metodo helper resolveDbType().

✕ Prima (hardcoded)

/** Seleziona il database */
private static final DbType DB_SELEZIONATO
    = DbType.SQLITE;

✓ Dopo (variabile d'ambiente)

/** Legge DB_TYPE da env (SQLITE o MYSQL) */
private static final DbType DB_SELEZIONATO
    = resolveDbType();

Modifica 2 — Parametri di connessione MySQL

Ogni parametro legge prima la variabile d'ambiente corrispondente; se assente o vuota, usa il valore di default originale. Il comportamento in locale rimane invariato.

✕ Prima (valori fissi)

private static final String MYSQL_HOST
    = "localhost";
private static final int MYSQL_PORT
    = 3306;
private static final String MYSQL_DATABASE
    = "calcolatrice_db";
private static final String MYSQL_USER
    = "serverrest";
private static final String MYSQL_PASSWORD
    = "calcolatrice";

✓ Dopo (variabili d'ambiente)

private static final String MYSQL_HOST
    = envOr("MYSQL_HOST",     "localhost");
private static final int MYSQL_PORT
    = Integer.parseInt(
        envOr("MYSQL_PORT", "3306"));
private static final String MYSQL_DATABASE
    = envOr("MYSQL_DATABASE", "calcolatrice_db");
private static final String MYSQL_USER
    = envOr("MYSQL_USER",     "serverrest");
private static final String MYSQL_PASSWORD
    = envOr("MYSQL_PASSWORD", "calcolatrice");

Modifica 3 — Metodi helper privati

Due metodi statici privati agiunti nella sezione dei metodi privati della classe. Non modificano nessuna logica esistente: servono solo alla sezione di configurazione.

DatabaseManager.java// Restituisce DbType.MYSQL se la variabile d'ambiente DB_TYPE vale "MYSQL" (case-insensitive);
// in tutti gli altri casi (variabile assente, vuota, o "SQLITE") restituisce DbType.SQLITE.
private static DbType resolveDbType() {
    return "MYSQL".equalsIgnoreCase(System.getenv("DB_TYPE"))
           ? DbType.MYSQL : DbType.SQLITE;
}

// Legge il valore della variabile d'ambiente `name`;
// se non esiste o è blank, restituisce il valore di default `def`.
private static String envOr(String name, String def) {
    String v = System.getenv(name);
    return (v != null && !v.isBlank()) ? v : def;
}

3 Il Dockerfile con supporto MySQL

Il progetto include due Dockerfile con supporto MySQL: Dockerfile per macOS e Dockerfile.win per Windows. Entrambi usano un multi-stage build e aggiungono rispetto alla versione base (solo SQLite) il download automatico dei driver JDBC (sqlite-jdbc e mysql-connector-j). Le differenze principali riguardano la directory di lavoro, l'immagine di runtime e il meccanismo di configurazione della porta.

🍎 macOS — Dockerfile

Dockerfile# ── Stage 1: Build ──────────────────────────────────────────
FROM eclipse-temurin:24-jdk AS build

# Installa Apache Ant e curl (necessari per la build e per scaricare i driver)
RUN apt-get update && apt-get install -y ant curl && rm -rf /var/lib/apt/lists/*

# Crea la directory di lavoro
WORKDIR /build

# Copia i file necessari per la build
COPY lib/        lib/
COPY src/        src/
COPY build.xml   .
COPY manifest.mf .
COPY nbproject/  nbproject/

# Scarica i driver JDBC: sqlite-jdbc (non tracciato in git) e mysql-connector-j
RUN curl -fsSL \
      "https://github.com/xerial/sqlite-jdbc/releases/download/3.46.1.3/sqlite-jdbc-3.46.1.3.jar" \
      -o lib/sqlite-jdbc.jar \
 && curl -fsSL \
      "https://repo1.maven.org/maven2/com/mysql/mysql-connector-j/8.4.0/mysql-connector-j-8.4.0.jar" \
      -o lib/mysql-connector-j.jar

# Compila e crea il JAR tramite Ant
RUN ant jar

# ── Stage 2: Runtime ─────────────────────────────────────────
FROM eclipse-temurin:24-jdk

WORKDIR /app

# Copia il JAR prodotto e tutti i driver JDBC
COPY --from=build /build/dist/ServerRest.jar          dist/ServerRest.jar
COPY --from=build /build/lib/gson-2.13.2.jar          lib/gson-2.13.2.jar
COPY --from=build /build/lib/sqlite-jdbc.jar          lib/sqlite-jdbc.jar
COPY --from=build /build/lib/mysql-connector-j.jar    lib/mysql-connector-j.jar

# Espone la porta del server REST
EXPOSE 8080

# Avvia il server; il database è configurato tramite la variabile d'ambiente DB_TYPE.
# Il numero di porta può essere sovrascritto passando un argomento: docker run ... image 9090
ENTRYPOINT ["java", \
    "-cp", "dist/ServerRest.jar:lib/gson-2.13.2.jar:lib/sqlite-jdbc.jar:lib/mysql-connector-j.jar", \
    "serverrest.App"]
CMD ["8080"]

🪟 Windows — Dockerfile.win

FROM eclipse-temurin:24-jdk AS build

 && curl -fsSL \

Spiegazione delle istruzioni aggiunte

IstruzionePerché è stata aggiunta
apt-get install ant curl Installa Apache Ant (necessario per la build del progetto NetBeans) e curl (per scaricare i driver JDBC). L'immagine base eclipse-temurin:24-jdk non li include.
curl ... sqlite-jdbc-3.46.1.3.jar Il file sqlite-jdbc.jar non è tracciato in git (da aggiungere manualmente per lo sviluppo locale). Il Dockerfile lo scarica automaticamente alla build.
curl ... mysql-connector-j-8.4.0.jar Driver JDBC per MySQL, non presente in precedenza. Viene scaricato da Maven Central e inserito in lib/ prima della compilazione Ant.
COPY --from=build /build/lib/... lib/ Ogni driver viene copiato singolarmente dal build stage al runtime stage, portando nel container solo i JAR necessari all'esecuzione.
...:lib/sqlite-jdbc.jar:lib/mysql-connector-j.jar nel classpath Entrambi i driver devono essere nel classpath a runtime: sqlite-jdbc per la modalità SQLite (default locale), mysql-connector-j per la modalità MySQL (container).
Multi-stage build — perché conviene
Lo Stage 1 (build) contiene JDK 24 + Ant + curl (~500 MB). Lo Stage 2 (runtime) usa la stessa immagine base ma senza strumenti di build: contiene esclusivamente il JAR compilato e i driver JDBC. L'immagine finale è più piccola e non espone compilatore né Ant.

4 Il file docker-compose.yml

Docker Compose orchestra i due servizi, la rete interna e il volume persistente in un unico file dichiarativo. Ecco il file completo con commenti esplicativi:

docker-compose.ymlversion: '3.8'

services:

  # ── Database MySQL ────────────────────────────────────────────────────────
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root_password      # password dell'utente root
      MYSQL_DATABASE:      calcolatrice_db    # crea automaticamente il database
      MYSQL_USER:          serverrest         # utente applicazione (non root)
      MYSQL_PASSWORD:      calcolatrice       # password utente applicazione
    volumes:
      # Script SQL eseguito automaticamente al primo avvio
      - ./sql/create_tables_mysql.sql:/docker-entrypoint-initdb.d/init.sql:ro
      # Volume Docker per la persistenza dei dati MySQL
      - mysql_data:/var/lib/mysql
    ports:
      - "3306:3306"   # opzionale: espone la porta sull'host per accesso diretto
    healthcheck:
      # Verifica che MySQL accetti connessioni prima di avviare il server
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-proot_password"]
      interval:     10s
      timeout:       5s
      retries:      10
      start_period: 30s   # margine per l'inizializzazione al primo avvio

  # ── Server REST Java ──────────────────────────────────────────────────────
  server:
    build: .                 # usa il Dockerfile nella directory corrente
    ports:
      - "8080:8080"
    environment:
      DB_TYPE:        MYSQL
      MYSQL_HOST:     mysql            # nome del servizio = hostname nella rete Docker
      MYSQL_PORT:     "3306"
      MYSQL_DATABASE: calcolatrice_db
      MYSQL_USER:     serverrest
      MYSQL_PASSWORD: calcolatrice
    depends_on:
      mysql:
        condition: service_healthy   # attende il healthcheck MySQL
    restart: on-failure             # riprova se MySQL non era ancora pronto

volumes:
  mysql_data:    # dichiarazione del volume gestito da Docker

Punti chiave del file

ElementoSpiegazione
MYSQL_DATABASE: calcolatrice_db L'immagine mysql:8.0 crea automaticamente questo database al primo avvio, prima di eseguire gli script di init.
MYSQL_USER / MYSQL_PASSWORD Crea un utente dedicato (non root) con accesso al solo database calcolatrice_db. Buona pratica di sicurezza.
/docker-entrypoint-initdb.d/init.sql MySQL esegue automaticamente tutti gli script in questa directory al primo avvio del container. Usato per creare la tabella operazioni.
healthcheck Docker testa periodicamente con mysqladmin ping se MySQL è pronto. Solo quando il test passa, il container è dichiarato healthy.
depends_on: condition: service_healthy Docker Compose non avvia il container server finché mysql non è dichiarato healthy. Previene errori di "connection refused" al bootstrap.
MYSQL_HOST: mysql Il server Java usa questo hostname per connettersi a MySQL. Docker risolve automaticamente mysql all'IP del container MySQL nella rete interna.
mysql_data:/var/lib/mysql I dati MySQL sono salvati in un volume Docker: sopravvivono al docker compose down e vengono eliminati solo con docker compose down -v.
start_period: 30s — perché è importante
Al primo avvio MySQL deve creare le strutture interne, impostare l'utente e il database, ed eseguire lo script init.sql. Questo richiede più tempo del normale. Il parametro start_period dice a Docker di non contare i fallimenti del healthcheck nei primi 30 secondi: impedisce che il container venga dichiarato unhealthy prima che abbia finito di inizializzarsi.

5 Build e avvio del sistema

Un singolo comando si occupa di tutto: compilare il JAR Java, scaricare i driver JDBC, costruire l'immagine Docker e avviare entrambi i container.

# Dalla cartella radice del progetto (dove si trova docker-compose.yml)
docker compose up -d --build

Cosa fa questo comando passo per passo

  1. Legge docker-compose.yml e identifica i due servizi: mysql e server.
  2. Esegue il multi-stage build del Dockerfile: installa Ant, scarica i driver JDBC, compila il progetto con ant jar, crea l'immagine runtime Alpine con solo il JAR e le lib.
  3. Scarica l'immagine mysql:8.0 da Docker Hub (solo al primo avvio, poi è in cache).
  4. Avvia il container mysql e inizia i healthcheck ogni 10 secondi.
  5. Attende che MySQL superi il healthcheck (fino a 10 tentativi × 10 secondi = 100 secondi).
  6. Avvia il container server con le variabili d'ambiente definite in docker-compose.yml.
  7. Il flag -d (detached) fa girare tutto in background: il terminale è subito libero.

7 Persistenza dei dati con i volumi

Il volume Docker mysql_data è il meccanismo che rende i dati MySQL indipendenti dal ciclo di vita del container. Senza volume, ogni docker compose down distruggerebbe il database.

ComandoCosa succede ai dati
docker compose down I container vengono fermati e rimossi. Il volume mysql_data sopravvive: al prossimo up, MySQL ritrova tutti i dati.
docker compose down -v I container e il volume vengono eliminati. Il database viene azzerato. Utile per un reset completo in sviluppo.
docker compose stop I container vengono sospesi (non rimossi). Il volume non è toccato.
docker compose up -d (senza --build) Riavvia i container esistenti. Se il volume esiste già, MySQL usa i dati precedenti senza rieseguire lo script di init.
Lo script init.sql viene eseguito solo al primo avvio
La cartella /docker-entrypoint-initdb.d/ viene elaborata da MySQL solo quando il volume è vuoto (primo avvio o dopo down -v). Nelle esecuzioni successive MySQL trova già i propri file di sistema nel volume e salta l'inizializzazione. Non preoccuparsi: la tabella operazioni viene comunque creata da DatabaseManager.initSchema() che usa CREATE TABLE IF NOT EXISTS.

Ispezionare il volume

# Elenco di tutti i volumi Docker presenti nel sistema

9 Problemi comuni

Problema: il server Java si avvia e si chiude subito
MySQL non era ancora pronto quando il server ha tentato la connessione, oppure le credenziali sono errate.

Diagnostica: 
docker compose logs server
# Cerca: "Errore di connessione al database: ..."
Soluzione: il parametro restart: on-failure fa sì che Docker riavvii automaticamente il server. Se il problema persiste, verificare che le variabili MYSQL_USER e MYSQL_PASSWORD in docker-compose.yml corrispondano esattamente a quelle del servizio mysql.
Problema: mysql rimane in stato "health: starting" a lungo
Al primo avvio MySQL esegue l'inizializzazione completa (create database, utente, tabelle): può richiedere 30–60 secondi.

Soluzione: attendere. Monitorare con: 
docker compose logs -f mysql
# Attendere il messaggio: "ready for connections"
Problema: "Communications link failure" nel log Java
Il server non riesce a raggiungere MySQL. Le cause più comuni:
  • La variabile MYSQL_HOST non è impostata o ha un valore errato (deve essere mysql, non localhost)
  • Il container MySQL non è in stato healthy: controllare con docker compose ps
  • Il container server è stato avviato prima del healthy di MySQL: docker compose restart server
Problema: la build Ant fallisce con "file not found: sqlite-jdbc.jar"
Il comando curl per scaricare sqlite-jdbc è fallito (problema di rete durante la build).

Soluzione: verificare la connessione internet e rieseguire: 
docker compose build --no-cache server
Problema: "port is already allocated" sulla porta 8080 o 3306
Un altro processo sull'host usa già quella porta.

Soluzione: modificare il mapping in docker-compose.yml (es. "8081:8080" per il server o "3307:3306" per MySQL), oppure fermare il processo che occupa la porta.
Riepilogo del workflow completo
  1. Assicurarsi che Docker Desktop (o Docker Engine) sia in esecuzione.
  2. Dalla cartella radice del progetto, eseguire docker compose up -d --build.
  3. Attendere che docker compose ps mostri entrambi i container in stato Up.
  4. Testare con curl http://localhost:8080/.
  5. In caso di problemi, consultare i log con docker compose logs -f.
